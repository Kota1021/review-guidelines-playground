# 本質 — 言語非依存

言語に依らない「何が良いコードか」。各項目はレシピでなく原理そのもの。違反を浮かび上がらせる手順は [review-techniques.md](./review-techniques.md) に置く。

これらは絶対則でなく原理。永続化データや外部システムとの互換、業務上の確定理由、既存コードとの一貫性のための逸脱はありうる。逸脱の根拠が diff やその議論から読み取れる場合は指摘しない。

スコープは設計・構造の品質。ロジックの仕様適合、セキュリティ、性能、テスト戦略は別軸のレビュー観点であり、本書は網羅しない（ここに無いことは重要でないことを意味しない）。それらは各分野の基準・ツールで別途確認する。

## 型・状態

- **型の住人 = 有効状態** — 型が表現しうる値の集合（住人）が、ドメイン上有効な状態の集合と一致する。不可能な状態を構築できる余剰の自由度を排除し、表現できない有効状態を残さない。住人が有効状態より多ければ不正状態が構築でき、少なければ表現力不足。
- **SSOT / 非冗長** — 各事実は唯一の権威ある源を持つ。他の値から導出できる状態を別途保持せず、導出する。冗長な表現は同期ずれの温床。
- **不変条件は全流入経路で保証** — 値が満たすべき条件は、その値が入りうる全ての経路（初期化・外部入力・更新）で保証される。特定のイベント経路にだけ検証を置かない。
- **寿命 = 利用区間** — 状態を持つ単位の寿命は、その状態が意味を持つ区間と一致する。区間より長寿命だと、前回の値が残り次の利用に漏れる。
- **一過性の出来事はイベントで表す** — 完了・エラー発生のような一度きりの事実は、残り続ける値の「変化」で観測するのでなくイベントとして表す。値の変化に頼ると、同じ値の再発生や再設定で検知が壊れる。

## 構造・関心

- **関心の分離 / 目的整合性** — 一つの単位は単一の目的に凝集し、異なる理由で変わるものは分ける。複数の関心が同居したら分割する。
- **依存方向** — 依存は安定・抽象の方へ向く。下位・汎用（被利用側）の部品が、上位・特定の利用者の都合を抱え込まない。利用者が複数の小さな部品を合成する側に立つ。
- **カプセル化 / 最小知識** — 内部を隠し契約だけ晒す。利用側に必要以上の知識・到達経路を与えない（デメテル）。
- **重複の排除と誤った抽象の回避** — 本質的に同一の概念は単一の源に統一する。一方で偶然似ているだけのものを早期共通化しない。
- **明示的依存** — 暗黙のグローバル・シングルトンより、引数・コンストラクタで依存を渡す。

## 命名

- **名前 = 実装** — 名前は実際にやること全てを表し、やらないことを表さない。内包する要素・目的が変わったら名前を見直す。
- **識別子の一意性** — 同一性が意味を持つ識別子（計測名・キー・通知名）を、別概念と共有しない。
- **抽象レベルの一貫性** — 同一スコープで抽象度を混ぜない。略語で意味を削らない。

## 失敗・副作用

- **エラーを握り潰さない** — 文脈を付けて伝播し、全ての離脱経路で状態を整合させる。
- **副作用の隔離・冪等性・CQS** — 副作用は端に寄せる。再試行・重複実行されうる境界では冪等性（または idempotency key）を設計する。本質的に非冪等な操作（例: 追記、課金）は、重複実行時の扱いを別途定義する。状態を変える操作と読み取る操作を分ける。
- **変更は意図した効果に限る** — 一つの変更が、無関係な既存の挙動を黙って変えない（意図しない退行を作らない）。これは差分の大小でなく「意図した範囲だけが変わる」こと。

## 複雑性

- **深いモジュール** — インターフェースは狭く、実装は深く。薄いラッパーを量産しない。
- **YAGNI** — 現在の要件に作る。まだ誰も必要としない一般化・拡張点を足さない。
- **複雑性の最小化 > 差分の少なさ** — 概念を正しく表すことを、差分を小さく保つことより優先する。全体の複雑性を下げる大きめの変更は、複雑性を上げる小さなパッチワークに勝る。
