# 確認手順（具象）

[本質](./principles.md)の違反を浮かび上がらせる手順。これらは**手段**であって目的ではない。各変更に合うものを当て、候補は必ず本質に対応づけ（引用し）てから報告する。どの本質にも対応づかないものは主観として破棄する。

2フェーズで進める。**Phase A（diff だけで完結する確認）の候補を先に書き出してから、Phase B（codebase 調査）に進む。** Phase B の探索に没入して Phase A を飛ばさない。特に大きな diff では注意が分散し、diff 構造の確認が抜けやすい。

## Phase A — diff 内で完結

1. **データフロー追跡** — 新規追加された状態ごとに「初期値の出所 / 更新経路 / 読み手」を辿る。イベント経路でしか更新されない値は、初期値・外部から渡された値に検証や処理が走らない。（diff 内で完結する新規状態は diff だけで、既存に跨る場合は diff 外も読む。）→ 不変条件は全流入経路で / 寿命 / 一過性はイベントで
2. **型の住人を数える** — 新規の型・引数群が取りうる値の組合せ（住人）を数え、ドメイン上の有効状態と突き合わせる。多ければ不可能な状態が構築でき（独立したフラグ・null 許容値の積、余分な選択肢）、少なければ表すべき有効状態が表せない。→ 型の住人 = 有効状態
3. **派生可能性チェック** — 新規に保持する状態が、既存の値や式から導出できないか。導出できるなら保持は冗長。→ SSOT / 非冗長
4. **境界変換の検査** — 失敗しうる変換（文字列→値型など）が、不正な入力を弾いて無効な値を構築せず、黙認で下流へ流していないか。→ 型の住人 = 有効状態 / エラーを握り潰さない
5. **関心の軸を列挙** — 変更された型・関数が変わりうる理由（関心の軸）を列挙する。2つ以上あれば目的の混在＝分割候補。下位・汎用の部品が特定利用者の都合を抱え込んでいないか。→ 関心の分離 / 目的整合性 / 依存方向
6. **層配置の確認** — 新規の型・ファイルが置かれた module / package と、それが依存・参照する概念の層を突き合わせる。依存グラフはビルド定義が SSOT。低レイヤーや汎用 module に置いた要素が、上位層や特定利用者の知識を抱え込んでいたら配置の誤り。→ 依存方向
7. **名前 × 実装の対応** — 新規シンボルの名前が表す範囲と、実装本体が実際に行うこと・内包する要素を突き合わせる。多い／少ない／ずれ。→ 名前 = 実装 / 抽象レベルの一貫性
8. **条件式 × 必須項目の突き合わせ** — 有効化・送信可否・早期 return の条件式を、必須／任意項目とエラー状態の一覧と照合し漏れを探す。→ 不変条件は全流入経路で
9. **挿入後の処理対象を確認** — 既存コード行間への挿入（分岐・case・引数の追加）で、後続の式・処理が挿入前後で何を対象にするかを比較し、既存挙動の退行がないか確認する。→ 変更は意図した効果に限る
10. **規約準拠の確認** — プロジェクト固有規約は、規約ドキュメントを読み既存コードを grep して確立した書き方を把握した上で、逸脱を指摘する。規約一覧をここにハードコードしない（ドキュメントと codebase が SSOT）。

## Phase B — codebase を調査（grep / read）

11. **列挙 → 既存概念の探索** — 新規追加シンボル（型・case・メソッド・プロパティ・コンポーネント・識別子。public/private 問わず）を列挙し、各概念について既存の類似物を探す。Grep は名前そのものでなく語幹・類義・regex で当てる。完全一致 grep は別名の類似概念に届かないので、Glob で同じ機能・ドメインのディレクトリを列挙し兄弟ファイルを読む手も併用する。見つかったら、まず「統合すべき単一概念か」（重複）を問い、別概念なら識別子を共有していないか（流用による混線）を確認する。→ 重複の排除 / 識別子の一意性
12. **定義元の確認** — diff だけでは語義・型・契約が確定しない名前（フラグ・プロパティ・引数）は、その定義元（型定義・モデル・doc コメント・生成スキーマ）を読む。名前の意味と diff 内の使われ方がズレていたら命名か用法の誤り。→ 名前 = 実装 / 型の住人 = 有効状態
13. **粒度の照合** — 手順5で疑った型について、既存の同種部品（同種の型・コンポーネント）を読み、新規追加の粒度がそれらから外れていないか照合する。→ 関心の分離 / 目的整合性 / 依存方向

## 報告前のバリデーション

各候補について: (a) diff の新規・変更箇所が対象か、(b) 本質を1つ引用できるか（できなければ主観として破棄）、(c) 実コードと一致するか（読んで確認したか）、(d) 行番号が head 側の絶対行か。Phase B で見つけた既存物のパスは、本質違反を裏づける根拠として使う。コードから確定できない仕様依存の疑いは、断定でなく質問として残す。

## 投稿・CI の知見

CI で LLM レビュアーを動かす際の運用上の要点:

- **レビュー基準を base から復元してから動かす。** PR head 上で動かすと、PR が同一 PR 内で基準（ガイドライン・skill）を書き換えてレビューを乗っ取れる。base ref から指示ファイルを checkout してから評価する。
- **インラインコメントの API 形。** PR review を head commit SHA（`commit_id`）に対し、各ファイルの patch hunk ヘッダーから算出した **head 側ファイル絶対行（`RIGHT` 側）** で投稿する（diff 相対位置でない）。行の意味を誤ると API が弾く（HTTP 422）か誤位置に付く。
- **再実行の冪等化。** 投稿本文に head SHA を含む marker を入れ、現在の head が既にレビュー済みなら投稿をスキップする。さもないと手動再実行・再起動で重複する。
- **巨大 diff では出力を絞る。** 数千行を超えたら inline 投稿を重大度の高いものに絞り、その旨をサマリに記す。全部に inline を付けようとしない。
- **高シグナル出力。** 本質に対応づく明確な問題だけを出し、偽陽性をほぼ0に保つ。検出量は実行ごとにばらつくので、重大な問題を確度高く拾うことに価値がある。
- **モデル選択。** 利用するモデルは、ツール利用時の精度・コスト・安定性を実際の diff で試して決める。モデル名やサイズだけでなく、レビュー手順を守れるかを確認する。
- **クロスレビュー。** 別エンジン（別モデル、または人間）の独立レビューが本当の欠陥に収束し、一つでは見落とすものを拾う。
